# Research synthesis: why Windows App sessions drop when idle, and how a targeted jiggler should work

Synthesized 2026-11-04 from seven research reports. Confidence tags: **[primary]** means confirmed by a primary source (Microsoft Learn, Apple docs, open-source code, or a local experiment on this machine); **[reports]** means reported by users or secondary sources; **[inference]** means our reasoning, not confirmed by any source.

## Verdict

The hypothesis is **supported but not proven**. The mechanism, in plain words:

1. The remote Windows side disconnects on a timer that only user input to the remote session resets. Microsoft's own policy text says "press a key or move the mouse" keeps the session active [primary].
2. A system-wide Mac jiggler posts a mouse-move at wherever the cursor already is. macOS routes that event to the app that owns the window under the cursor, and keys go to the focused app [primary for the API, inference for routing].
3. Windows App is closed source and Microsoft documents nothing about background input. By normal Cocoa rules, it only receives mouse motion when its session window is under the pointer and the app is active [inference].
4. So the jiggle reaches the remote only when the session window happens to be frontmost with the cursor over it, which would explain "works sometimes" for the session [inference]. It explains remote Teams presence only if Teams presence comes from a path other than input injected into the session (see the discriminator below).
5. Remaining drops may also come from causes no Mac-side jiggler can fix: a lock that input does not prevent (forced or manual lock), RD Gateway or VPN timeouts, Mac sleep or App Nap, or network or UDP issues [primary for the policies, reports for the drops]. An inactivity-triggered lock is not in this list: it is driven by session idle, so real in-window input should also prevent it [inference].

The fix is to focus the session window, move the cursor inside it, and post a real mouse-move event (not a cursor warp) there. The claim still needs one empirical test on the user's machine before building.

**Discriminator from the user's own report (read this first).** The user says the system-wide jiggler keeps them Available in Teams on the remote PC while the session still drops sometimes. These two facts pull apart [inference]:

- If remote Teams reliably stays Available right up to each disconnect, input is probably reaching the remote session, the targeting hypothesis is weakened, and the cause is more likely gateway, VPN, network, a lock the jiggle cannot prevent, or Mac-side throttling (App Nap, display sleep).
- The hypothesis survives only if the Available status comes from somewhere else: Teams signed in on the Mac or a phone, which wins under the most-recently-active-device rule ([presence-admins](https://learn.microsoft.com/en-us/microsoftteams/presence-admins) **[primary]**), or Teams activity that does not depend on the jiggle.
- Not yet asked of the user: is Teams signed in on the Mac or phone, and does remote Teams stay Available until the moment of disconnect? Open questions 16 and 17 cover this.

## RDP idle disconnect mechanics

- The policy "Set time limit for active but idle Remote Desktop Services sessions" disconnects a session that has been idle "without user input" for the configured time. A warning appears two minutes before, and the user can "press a key or move the mouse to keep the session active." Default is unlimited; console sessions are exempt; Computer Configuration overrides User Configuration. **[primary]** [policy-csp-admx-terminalserver](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-terminalserver)
- "Set time limit for disconnected sessions" is a separate timer that starts after disconnect and controls when a disconnected session is logged off. **[primary]** [same page](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-terminalserver)
- "End session when time limits are reached" (fResetBroken) turns a time-out from a disconnect into a logoff. It applies "only to time-out limits explicitly set by the administrator" and not to "time-out events that occur due to connectivity or network conditions." This is the official line between an idle-policy disconnect and a network drop. **[primary]** [same page](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-terminalserver)
- The registry names MaxIdleTime and MaxDisconnectionTime (milliseconds, 0 = none) appear only in secondary sources. **[reports]** [itbiznetworks](https://itbiznetworks.com/2023/06/15/configuring-rdp-rds-sessions-limits-timeouts-on-windows/), [quantvps](https://www.quantvps.com/blog/how-can-i-keep-my-rdp-session-alive)
- Mouse, keyboard, touch, pen and trackpad are "peripheral reflection" redirections from local to remote, and Windows App is named as an RDP client. The doc does not say whether synthetic mouse moves reset the idle timer. **[primary]** [redirection-remote-desktop-protocol](https://learn.microsoft.com/en-us/azure/virtual-desktop/redirection-remote-desktop-protocol)
- Network keep-alives (TCP or RDP) stop network devices dropping the connection but do not count as user input and do not reset the idle timer. Microsoft's own "Configure keep-alive connection interval" policy (KeepAliveEnable/KeepAliveInterval) is described as the server checking session state at an interval, not as user input; one vendor (Royal TS) reports it does not stop idle disconnects. Microsoft's description was only seen via a policy mirror and search summary. **[reports]** [kapilarya policy description](https://gp.kapilarya.com/configure-keep-alive-connection-interval), [Royal TS thread](https://support.royalapps.com/support/discussions/topics/17000021203), [MS troubleshoot: keep-alive](https://learn.microsoft.com/en-us/troubleshoot/windows-server/remote/terminal-services-cannot-restart-keep-alive-enabled),  [quantvps](https://www.quantvps.com/blog/how-can-i-keep-my-rdp-session-alive), [slack.green](https://slack.green/en/blog/how-to-keep-remote-desktop-session-active)
- Session lock is a separate disconnect path. On AVD, Windows 365 and Windows 11 hosts with the relevant updates (KB5037770, KB5039211, KB5037782 or later), the default with Entra ID SSO is to disconnect the session on lock; with legacy authentication the default is to show the remote lock screen. Controlled by "Disconnect remote session on lock for Microsoft identity platform authentication" and the legacy equivalent. A remote lock can therefore produce a disconnect that looks like an idle disconnect, with no RDS idle policy set. If the lock came from an inactivity trigger (below), input that resets session idle should prevent the lock and so the disconnect; a manual or forced lock would not be prevented [inference]. **[primary]** [configure-session-lock-behavior](https://learn.microsoft.com/en-us/azure/virtual-desktop/configure-session-lock-behavior); users report the same **[reports]** [Tech Community thread](https://techcommunity.microsoft.com/discussions/azurevirtualdesktopforum/screensaver--lock-screen/4013699)
- Remote idle can lock the session through two mechanisms: the "Interactive logon: Machine inactivity limit" policy (registry InactivityTimeoutSecs, seconds, computer-level only) and a secure screen saver (ScreenSaveActive, ScreenSaverIsSecure, ScreenSaveTimeOut, described as "user idle time"). A locked session stays active; a disconnect is a different state. **[primary]** [troubleshoot RDS locks](https://learn.microsoft.com/en-us/troubleshoot/windows-server/remote/troubleshoot-unexpected-rds-session-locks-or-disconnections), [Policy CSP](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-localpoliciessecurityoptions) (the CSP page confirms the policy locks via screen saver after inactivity; it does not say which input events reset the timer). That injected RDP mouse input resets these timers is **[inference]**.
- The same troubleshooting page gives distinct client messages: an idle-timeout disconnect (MaxIdleTime) shows "Your Remote Desktop Services session ended because the remote computer didn't receive any input from you"; a connection-time limit shows "The remote session ended because the total logon time limit was reached." It also states that disconnections with no consistent timing pattern are more likely network issues than configuration. Whether Windows App on macOS shows the same text is unverified. **[primary]** [same page](https://learn.microsoft.com/en-us/troubleshoot/windows-server/remote/troubleshoot-unexpected-rds-session-locks-or-disconnections)
- The RDP protocol carries a disconnect reason: ERRINFO_IDLE_TIMEOUT = 0x00000003 ("idle session limit timer on the server has elapsed"), and the Win32 enum has exDiscReasonServerIdleTimeout = 3 (logoff by user = 12). Seen via search summaries of the spec pages, not read in full. **[primary, partly verified]** [MS-RDPBCGR Set Error Info](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/a21a1bd9-2303-49c1-90ec-3932435c248c), [ExtendedDisconnectReasonCode](https://learn.microsoft.com/en-us/windows/win32/termserv/extendeddisconnectreasoncode). **Cheap classifier:** note the exact disconnect dialog text, and on the remote PC check TerminalServices-LocalSessionManager/Operational for the disconnect reason; this separates idle policy from lock, gateway and network before any code is written.
- RD Gateway connection authorization policies have their own IdleTimeout and SessionTimeout (minutes, 0 = none) and a SessionTimeoutAction. The docs do not define what counts as idle at the gateway. **[primary]** [Win32_TSGatewayConnectionAuthorizationPolicy](https://learn.microsoft.com/en-us/windows/win32/termserv/win32-tsgatewayconnectionauthorizationpolicy)
- An AutoIt user ran a script inside the session that moved the mouse and pressed a key. It reset the session idle tooltip but a 10-minute security policy still ended the session. Single anecdote about a server-side script, and the thread was locked as a policy bypass. **[reports]** [AutoIt forum](https://www.autoitscript.com/forum/topic/203261-idletimer-inside-rdp-session/)
- Admins report the idle GPO sometimes failing to fire on AVD; fixes involved "End session when time limits are reached" and the disconnected-session limit. **[reports]** [Tech Community](https://techcommunity.microsoft.com/discussions/azurevirtualdesktopforum/idle-session-time-out-via-gpo-not-working/4385005)
- Connection type decides which policies apply [inference, from the docs above]: the Entra-SSO disconnect-on-lock default and Intune/host-pool settings apply to AVD, Windows 365 and Dev Box hosts; RD Gateway CAP IdleTimeout applies only if a gateway is in the path (the troubleshoot page notes users who bypass the RDGW are unaffected); a plain RDP PC on a VPN makes VPN or NAT idle the prime suspect. Which kind "Australia Desktop" is (Devices tab PC vs. Workspace feed, gateway or VPN) is not yet known; see Open question 15.
- The server idle timer is most likely reset by any input that arrives as keyboard or mouse events, including mouse-move, because Microsoft's own wording says "move the mouse." No primary source distinguishes clicks from moves, or hardware from injected input. One blog claims deprecated mouse_event scripts do not count; treat as weak. **[inference]** [codegenes](https://www.codegenes.net/blog/powershell-mouse-move-does-not-prevent-idle-mode/)
- Idle-policy disconnect versus network drop: an idle disconnect is server-initiated with a distinct message and reason code 3 (see above [primary]); the session stays running in the Disconnected state unless "End session" is set. The two-minute warning comes from the policy text [primary]. That a network drop usually triggers client auto-reconnect is **[inference]**, and the exact UI difference in Windows App on macOS is unverified.

## How Windows App forwards input

- Microsoft's Windows App macOS input documentation covers keyboard shortcut mapping, keyboard language, Scancode versus Unicode modes, trackpad gestures and right-click. It says nothing about focus requirements, background input, idle behavior or keep-alive. **[primary]** [input-keyboard-mouse-touch-pen](https://learn.microsoft.com/en-us/windows-app/input-keyboard-mouse-touch-pen)
- The known-issues page for macOS lists keyboard layout limits, UDP/RDP Shortpath disabled by default in 11.2.7 (user-defaults key ClientSettings.EnableAvdUdpSideTransport), Teams audio enumeration, keychain migration, screen capture protection and AutoUpdate. No idle-disconnect, keep-alive or background-input item. **[primary]** [troubleshoot-known-issues-limitations](https://learn.microsoft.com/en-us/windows-app/troubleshoot-known-issues-limitations)
- No client-side keep-alive or "prevent idle disconnect" setting appears in any Microsoft doc read. The legacy client's General preferences list only thumbnails, telemetry, Mac shortcuts, proxy, interpolation and hardware acceleration. A current Windows App settings page was not located (guessed URL 404), so absence in the current Settings is not fully verified. **[primary]** [client-features-macos](https://learn.microsoft.com/en-us/azure/virtual-desktop/users/client-features-macos)
- A Devolutions forum user reports a Mac keep-alive tool did not stop the remote lock screen while the Windows version of the same tool worked because it runs inside the RDP tool. Consistent with the hypothesis. **[reports]** [Devolutions forum](https://forum.devolutions.net/topics/42458/mouse-jiggler-for-mac)
- A Mac jiggler troubleshooting guide notes jigglers stop when you switch windows if set to "Only While App In Front," and that a caffeinate-style keep-awake sends no input so idle counters keep rising. **[reports]** [mousejigglermac](https://mousejigglermac.com/blog/mouse-jiggler-not-working-mac), [slack.green](https://slack.green/en/blog/how-to-keep-teams-active-on-mac)
- A Microsoft Q&A thread about a MacBook Air M3 disconnecting every 10 to 30 minutes points at network and UDP settings (an undocumented fSelectNetworkDetect=0, redirection, NIC power saving), not idle. Shows drops can be network-related. **[reports]** [Q&A](https://learn.microsoft.com/en-us/answers/questions/5856401/mac-m3-frequently-disconnects-from-windows-systems)
- Users also report random Windows App drops around Mac sleep or network loss, and one HP ZCentral thread (different product) found disabling App Nap fixed a similar timeout. **[reports]** [Tech Community idea](https://techcommunity.microsoft.com/idea/azurevirtualdesktop/windows-app-disconnects-my-remote-session-randomly/4274512), [Q&A](https://learn.microsoft.com/en-us/answers/questions/617106/microsoft-remote-desktop-keeps-getting-disconnecte), [HP forum](https://h30434.www3.hp.com/t5/HP-Z-Remote-Graphics-Software-RGS/ZCentral-times-out-on-a-mac-after-inactivity-Machine-crashes/m-p/7973746)
- No primary or user source states whether Windows App forwards pointer motion when it is not the frontmost app. By typical macOS mechanics, a Cocoa view gets mouseMoved only when its window is under the cursor and, unless tracking areas use activeAlways, usually only when the app is active; key events go only to the key window of the active app. **[inference]**
- Window naming: no Microsoft doc defines Windows App window titles on macOS. The only evidence is the user's observation: Connection Center is "Windows App," session windows are "<Name> Desktop" such as "Australia Desktop." Whether session windows are standard NSWindows exposing AX titles is likely but unverified. **[inference]** [client-features-macos](https://learn.microsoft.com/en-us/azure/virtual-desktop/users/client-features-macos), [Keyboard Maestro forum](https://forum.keyboardmaestro.com/t/list-all-windows-and-properties-of-app-km8/8937)
- No existing macOS tool that targets an RDP or Windows App window was found. Related material is generic: AppleScript GUI scripting of the RDC client is called fragile, and one article notes a click must land where the remote desktop is actually visible. Absence of results is not proof of absence. **[reports]** [Apple discussions](https://discussions.apple.com/thread/8347325), [MacScripter](https://www.macscripter.net/t/using-modifiers-with-rdp-windows-session/71824), [green-dotter](https://green-dotter.com/blog/keep-remote-desktop-session-alive)

## Teams presence

- Presence changes to Away if the desktop is inactive for more than five minutes. "Inactive" includes locking the computer, idle or sleep mode, or actively using the Teams mobile app instead of desktop. **[primary]** [presence-not-show-actual-status](https://learn.microsoft.com/en-us/troubleshoot/microsoftteams/teams-im-presence/presence-not-show-actual-status)
- The admin doc is vaguer: Away "if they're inactive for a few minutes or if the computer is locked," Offline when the computer sleeps. With multiple devices, the most recently active device determines presence. Manual status can only be less available than the calculated one, and the idle threshold is not configurable. **[primary]** [presence-admins](https://learn.microsoft.com/en-us/microsoftteams/presence-admins); a user found lock-to-Away only worked after removing the mobile app **[reports]** [Q&A](https://learn.microsoft.com/en-us/answers/a/8396355)
- Microsoft does not document which input signals Teams uses (keyboard, mouse, OS idle timer), nor anything about RDP-delivered input or VDI. **[primary, by absence]** [presence-not-show-actual-status](https://learn.microsoft.com/en-us/troubleshoot/microsoftteams/teams-im-presence/presence-not-show-actual-status)
- Community sources conflict: some say the desktop app uses the Windows session idle timer, others say it tracks in-app activity only. Users also report Away while the app is in the background on an unlocked, non-idle PC. **[reports]** [avnation](https://www.avnation.tv/?p=99971), [Tech Community](https://techcommunity.microsoft.com/t5/microsoft-teams/teams-status-change-to-away-if-teams-desktop-application-is-in/td-p/3572779), [Tech Community](https://techcommunity.microsoft.com/t5/microsoft-teams/what-are-the-teams-presence-status-change-timings-away-offline/m-p/2637990)
- A Mac-side author measured that Teams-style Away detection uses the CGEventSource input idle counter, that IOPMAssertionDeclareUserActivity did not reset it, and that a neutral flagsChanged event does. **[reports]** [dev.to](https://dev.to/christianmusumeci00/why-stay-awake-apis-dont-keep-you-green-on-teams-385e)
- Input only counts for the remote Teams if it is actually injected into the remote session. The system-wide jiggler keeps remote Teams Available only while the session window happens to be frontmost with the cursor over it, which matches "works sometimes." Input that arrives as real RDP mouse or keyboard events should plausibly reset Teams idle if Teams reads OS idle, but mouse-only versus keystroke is unknown. **[inference]**
- Because the Teams Available effect may come from a different path (local Mac idle if presence is synced, or an app signal), treat presence as a side benefit, not proof the jiggle reached the session. **[inference]**

## Why system-wide jigglers fail

- `CGEvent.post(tap:)` injects a Quartz event into the system event stream at the chosen tap location. Apple's page says nothing about which app receives it; routing to the window under the pointer is standard WindowServer behavior but not stated there. **[primary]** [CGEvent.post(tap:)](https://developer.apple.com/documentation/coregraphics/cgevent/post(tap:).md)
- `CGWarpMouseCursorPosition` moves the cursor "without generating or posting an event." A warp alone delivers nothing to any app. **[primary]** [CGWarpMouseCursorPosition](https://developer.apple.com/documentation/coregraphics/cgwarpmousecursorposition(_:).md)
- sjova/jiggle builds a synthetic mouseMoved with a `.hidSystemState` source, posts it to `.cghidEventTap`, moves the cursor 16px left and right after an idle threshold read from `CGEventSource.secondsSinceLastEventType(.hidSystemState)`, and holds PreventUserIdleSystemSleep and PreventUserIdleDisplaySleep assertions. It does no per-app or per-window targeting. **[primary]** [sjova/jiggle](https://github.com/sjova/jiggle), [jiggle.swift](https://raw.githubusercontent.com/sjova/jiggle/main/jiggle.swift)
- FreeJig moves the pointer "within the selected range on its current display," sends clicks, scrolls and Shift "at the current pointer position," needs Accessibility, and has a Silent mode that only holds a power assertion. No per-window targeting. **[primary]** [FreeJig](https://github.com/tom10271/FreeJig)
- AlwaysJiggle "posts real input events" to reset the idle timer read by Slack and Teams; no targeting of any app. **[primary]** [alwaysjiggle](https://github.com/ncesar/alwaysjiggle)
- KeepingYouAwake is a wrapper around caffeinate: sleep prevention only, no input. **[primary]** [KeepingYouAwake](https://github.com/newmarcel/KeepingYouAwake). Stick Software's Jiggler "fakes mouse movement" and has a Zen mode; its source was not read. **[reports]** [Stick Software](https://www.sticksoftware.com/software/Jiggler.html), [Macworld](https://www.macworld.com/article/173800/jiggler-2.html)
- Two designs, two effects: event-posting jigglers reset macOS HID idle time (keeping Mac-side Teams Available), while power-assertion tools only prevent sleep and send no input anywhere. **[inference]**
- Why the jiggle misses the remote: (1) a HID-tap mouseMoved goes to the app owning the window under the cursor and keys go to the focused app, so nothing targets the RDP client; (2) if the session window is not frontmost or the cursor is elsewhere, Windows App never sees the event and the remote idle or lock policy fires while Mac-side Teams stays Available; (3) a few-pixel move over a non-RDP area is never translated into remote coordinates; (4) a warp-only tool generates no event at all. **[inference]**
- The server-side fix is to raise or disable the Session Time Limits policy, which the user may not control. **[reports]** [Q&A](https://learn.microsoft.com/en-gb/answers/questions/2046662/i-want-to-keep-the-rd-clients-session-going), [anyviewer](https://www.anyviewer.com/how-to/keep-rdp-session-alive-0007.html)

## macOS APIs

### Idle detection and the synthetic-event subtlety

- `CGEventSource.secondsSinceLastEventType(_:eventType:)` returns seconds since the last event of a type in a state table; pass `kCGAnyInputEventType` (`CGEventType(rawValue: ~0)` in Swift) for any keyboard, mouse or tablet input. **[primary]** [secondsSinceLastEventType](https://developer.apple.com/documentation/coregraphics/cgeventsource/secondssincelasteventtype(_:eventtype:).md)
- State tables: `combinedSessionState` combines all sources posting to the login session; `hidSystemState` reflects hardware sources from the HID system; `privateState` is per-source. Apple does not say whether synthetic events reset each table. **[primary]** [CGEventSourceStateID](https://developer.apple.com/documentation/coregraphics/cgeventsourcestateid.md)
- Local experiment on this machine (macOS 27.0, posting a `.mouseMoved` at the current cursor with ~3s idle): source hidSystemState posted to `.cghidEventTap` reset hid idle, combined idle and ioreg HIDIdleTime; source combinedSessionState posted to `.cgSessionEventTap` reset only combined idle, and hid idle plus HIDIdleTime kept climbing; combinedSessionState posted to `.cghidEventTap` reset all three; privateState posted to `.cghidEventTap` reset both CGEventSource counters but not HIDIdleTime (reproduced twice). Single-machine result. **[primary, local experiment]**
- Therefore the tap location, not just the source state, decides whether HID-level idle resets. `hidSystemState` is a reliable "real hardware only" signal only if your own posts go to `.cgSessionEventTap`. **[inference from experiment]**
- A StayActive commit claims `.hidSystemState` never reports synthetic events, and a fidget issue says hidSystemState misses software clicks. Both match the experiment only for session-tap posts. **[reports]** [StayActive PR](https://github.com/ostd6212/StayActive/pull/1), [fidget issue](https://github.com/omesser/fidget/issues/1858)
- IOKit HIDIdleTime (`ioreg -c IOHIDSystem`) is reset by real mouse movement and by synthetic events posted into IOHIDSystem; DockDoor bug reports show synthetic activity kept idle under ~8s and prevented display sleep. **[reports]** [til](https://github.com/jbranchaud/til/blob/master/mac/detect-how-long-a-user-has-been-idle.md), [DockDoor 1648](https://github.com/ejbills/DockDoor/issues/1648), [DockDoor 1634](https://github.com/ejbills/DockDoor/issues/1634), [dssw](https://www.dssw.co.uk/powermanager/guide/finding-and-fixing/inactivity/)
- Reading idle via `secondsSinceLastEventType(.hidSystemState, ...)` reportedly works without Input Monitoring; the experiment could not verify a clean-permission case. **[reports]** [shortcutlens issue](https://github.com/MHusted01/shortcutlens/issues/39)
- Hazard: revoking Accessibility while an active CGEventTap exists can hang system input until restart. Poll idle instead of installing taps. **[reports]** [Apple forums 844416](https://developer.apple.com/forums/thread/844416), [Apple forums 735204](https://developer.apple.com/forums/thread/735204)

### Window enumeration: Screen Recording versus Accessibility

- `kCGWindowName` from `CGWindowListCopyWindowInfo` is nil for other apps' windows on 10.15+ unless the caller has Screen Recording. An Apple DTS engineer says it "seems to be gated by the Screen Recording user data protection"; the OP's fix was granting Screen Recording, not Accessibility. Owner name, owner PID and window number were still returned. Chromium uses the same signal to detect the permission. **[primary]** [Apple forums 126860](https://developer.apple.com/forums/thread/126860), [Chromium permissions_utils.mm](https://chromium.googlesource.com/chromium/src/+/711ab9bc/ui/base/cocoa/permissions_utils.mm)
- `CGPreflightScreenCaptureAccess()` and `CGRequestScreenCaptureAccess()` check and request Screen Recording. They are public APIs since macOS 10.15 (from model knowledge; the Apple page body could not be retrieved, so availability is not quoted from Apple). **[inference, high confidence]** [CGWindowListCopyWindowInfo](https://developer.apple.com/documentation/coregraphics/cgwindowlistcopywindowinfo(_:_:))
- Reading titles through the Accessibility API (`AXUIElementCreateApplication`, `kAXWindowsAttribute`, `kAXTitleAttribute`) needs only Accessibility trust. Standard practice in projects like Mission Control Turbo, but no explicit Apple statement found. **[inference]** [MCT AccessibilityBridge.swift](https://tangled.org/pierrelf.com/mct/blob/main/MCT/API/AccessibilityBridge.swift)

### Activation and raise

- Cooperative activation (macOS 14+): activation is a request the system may decline. `NSRunningApplication.activate(from:options:)` returns whether it was allowed; the documented flow is for the active app to call `NSApp.yieldActivation(to:)` first. Only the active app can influence the activation context, so a background menu bar app may be refused. **[primary]** [cooperative activation](https://developer.apple.com/documentation/appkit/passing-control-from-one-app-to-another-with-cooperative-activation.md), [activate(from:options:)](https://developer.apple.com/tutorials/data/documentation/appkit/nsrunningapplication/activate(from:options:).md)
- Common raise recipe: activate the owning app, create the AX element for its pid, iterate `kAXWindowsAttribute`, match by title, then `AXUIElementPerformAction(window, kAXRaiseAction)`; optionally set `kAXFrontmostAttribute` and check every return code because AX calls fail silently. `_AXUIElementGetWindow` is a private symbol used by AltTab, Rectangle and yabai to map AX windows to CGWindowIDs. AX raise is best-effort. **[reports]** [MCT](https://tangled.org/pierrelf.com/mct/raw/main/MCT/API/AccessibilityBridge.swift), [SwiftShift PR 162](https://github.kakarurec.workers.dev/pablopunk/SwiftShift/pull/162), [paneru](https://docs.rs/crate/paneru/latest/source/src/manager/windows.rs)
- Activation since Big Sur can bring forward more windows than wanted (thread title only seen). **[reports]** [Apple forums 668913](https://developer.apple.com/forums/thread/668913)

### Posting events

- `CGPreflightPostEventAccess` and `CGRequestPostEventAccess` are public CoreGraphics APIs (macOS 10.15+) for checking and requesting permission to post events (from model knowledge; the Apple page bodies could not be retrieved, so treat as unverified against Apple). Posting CGEvents is gated by the PostEvent TCC class, shown to users under Accessibility, per forum and blog sources. Listening via CGEventTap is the separate Input Monitoring permission. `CGEvent.post` is reportedly blocked under App Sandbox and has drawn App Store rejections. **[reports]** [Apple forums 820594](https://developer.apple.com/forums/thread/820594), [dev.to quicopy](https://dev.to/quicopy/shipping-global-keyboard-shortcuts-on-macos-sandbox-the-part-apple-doesnt-document-57no), [dev.to christianmusumeci00](https://dev.to/christianmusumeci00/why-stay-awake-apis-dont-keep-you-green-on-teams-385e), [Apple discussions Japan](https://discussionsjapan.apple.com/thread/110194517)
- macOS checks the post-event permission at launch, so relaunch after granting. **[reports]** [dev.to](https://dev.to/christianmusumeci00/why-stay-awake-apis-dont-keep-you-green-on-teams-385e)
- `postToPid` evidence is thin: one answer says it is only for keyboard events; a developer found a background app still needed focus; a related thread has no replies. **[reports]** [Stack Overflow mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/75511477/how-to-post-to-event-to-specific-window-on-macos), [Apple forums 724835](https://developer.apple.com/forums/thread/724835), [Apple forums 744024](https://developer.apple.com/forums/thread/744024)
- Coordinates: CGEvent positions use global coordinates with a top-left origin on the main display; AppKit frames use bottom-left; AX position and size use the CG top-left convention. Convert with cgY = mainScreenHeight - appKitY. **[inference]**
- `AXIsProcessTrustedWithOptions` with the prompt option is the only supported way to request Accessibility; TCC ties the grant to code signature, bundle id and path, so ad-hoc builds can lose the grant on rebuild. Reset stale entries with `tccutil reset Accessibility <bundle-id>`. **[reports]** [Apple forums 66151](https://developer.apple.com/forums/thread/66151), [openclaw permissions](https://docs.openclaw.ai/mac/permissions), [SO mirror 29006379](https://kiwix.lib.lema.org/stackoverflow.com_en_all_2023-11/questions/29006379/accessibility-permissions-reset-after-application-update), [SO mirror 20151177](https://kaweah.freedombox.rocks/kiwix/content/stackoverflow.com_en_all_2023-11/questions/20151177/axisprocesstrustedwithoptions-unchecks-privacy-accessibility-checkbox-when-app)

### Packaging

- A SwiftPM executable target with `main.swift` importing AppKit builds, and `@testable import` of the executable target works with `swift test` on this machine (Swift 6.4, macOS 27, tools-version 5.9). Top-level code in main.swift does not run under tests. **[primary, local experiment]**
- Historically executables were not testable because of the main-symbol conflict; the safe pattern is a library target plus a thin executable. `@main` was not tested on this toolchain. **[reports]** [SR-13651](https://bugs.swift.org/browse/SR-13651), [SR-1503](https://bugs.swift.org/browse/SR-1503)
- Manual .app assembly works: `Contents/MacOS/<exe>` plus `Contents/Info.plist` (CFBundleIdentifier, CFBundleExecutable, CFBundlePackageType=APPL, LSUIElement=true, LSMinimumSystemVersion, NSPrincipalClass=NSApplication). `codesign -s - --force` produced an ad-hoc signature and `codesign --verify --strict` passed. Runtime launch was not tested. No `-sectcreate` plist is needed when shipping a real bundle. **[primary, local experiment; inference for the sectcreate point]**
- `SMAppService.mainApp` (macOS 13+) offers register, unregister, status (.notRegistered, .enabled, .requiresApproval, .notFound) and `openSystemSettingsLoginItems()`. From model knowledge; the Apple page body was not retrievable. Registering from outside /Applications or ~/Applications is unverified. **[inference]** [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)
- MenuBarExtra has no API for presentation state, the status item or the popup window, and labels are limited; developers move to NSStatusItem for dynamic items. **[reports]** [MenuBarExtraAccess](https://www.github.com/orchetect/MenuBarExtraAccess), [multi.app](https://multi.app/blog/pushing-the-limits-nsstatusitem), [zenn.dev](https://zenn.dev/kyome/articles/58d89dc746e0dc)
- `IOPMAssertionCreateWithName` with PreventUserIdleSystemSleep keeps the system awake without forcing the display on; PreventUserIdleDisplaySleep keeps the display on. `pmset -g assertions` shows them. **[reports]** [VS Code nosleep_macos.rs](https://github.com/microsoft/vscode/blob/91773ced4b737525a7d9a3c3d03369fdd0bac182/cli/src/tunnels/nosleep_macos.rs), [keepawake](https://docs.rs/crate/keepawake/latest/source/src/sys/macos.rs)
- Whether display sleep or Mac screen lock alone breaks a Windows App session was not established. System sleep will drop it; a locked or dark Mac may stop synthetic input or focus from working. **[inference]**
- App Nap as an alternative explanation. Apple's archived Energy Efficiency Guide says App Nap reduces an app's CPU use and timer frequency, and that apps holding IOKit power-management or NSProcessInfo activity assertions are not napped. **[primary, archived]** [AppNap guide](https://developer.apple.com/library/content/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html). Whether a backgrounded, occluded Windows App is napped, and whether that would starve its RDP heartbeat, is unknown. A local check found no `NSAppSleepDisabled` key in Windows App's Info.plist, so it is not opted out in the plist (that does not show whether it uses an activity assertion at runtime). The per-app `defaults write <bundle-id> NSAppSleepDisabled -bool YES` override comes only from forum posts, one of which says it did nothing. **[reports]** [Xojo forum](https://forum.xojo.com/t/prevent-app-nap/13174). The HP ZCentral precedent is a different product with the same failure shape. If App Nap is the cause, periodically foregrounding the window would help for a different reason than input targeting [inference]. Check `pmset -g assertions`, Activity Monitor's App Nap column, and `pmset -g log` around a drop.
- Whether the Mac's display sleeps or locks during the user's away period is unknown. A locked Mac blocks activation and event posting, so the app's loop could not run; the app may need to hold a display-sleep assertion [inference].

## Design implications

1. **Run the decisive experiment before building.** Connect, put the session window frontmost, jiggle only inside it, and see whether the disconnect still happens. If it persists with real in-window input, the cause is more likely a gateway, VPN, network or Mac-side throttling cause, or a forced lock, not the jiggler's targeting (an inactivity lock should be prevented by the same input [inference]). Do the cheaper classification first: read the disconnect dialog text and the remote disconnect reason code (see RDP mechanics), and answer the Teams discriminator. (Tied to: Windows App forwarding is undocumented [inference]; multiple disconnect causes exist [primary].)
2. **Target the session window, not the cursor's current spot.** Activate com.microsoft.rdc.macos, AXRaise the session window, warp the cursor inside its content rect, then post `.mouseMoved` events there. This is the gap that sjova/jiggle, FreeJig and AlwaysJiggle leave open. (Tied to: existing jigglers post at the current pointer position [primary].)
3. **Post a real event, never warp alone.** `CGWarpMouseCursorPosition` generates no event. Use `CGEvent(mouseEventSource:mouseType:.mouseMoved...)` and post it. (Tied to: Apple's warp doc [primary].)
4. **Move by several pixels and back, and optionally add a harmless key.** Microsoft says "move the mouse" counts, but whether a 1 to 2px move changes the remote cursor position under Retina scaling is untested and unsourced (use several pixels as a precaution), and whether mouse-only motion resets Teams idle is unknown. Make an F15 or Shift keystroke a setting. (Tied to: idle policy text [primary]; Teams signal undocumented [primary by absence].)
5. **Find windows with Accessibility, not CGWindowList names.** Match `kAXTitleAttribute`, skip "Windows App" (Connection Center), treat other titled windows such as "Australia Desktop" as session candidates, and let the user pick the target in the menu. Use CGWindowList only for bounds. This avoids a second Screen Recording prompt. (Tied to: kCGWindowName gating [primary].)
6. **Do not assume activation succeeds.** A background agent's `activate()` may be declined under cooperative activation. Follow it with `kAXFrontmostAttribute` and `kAXRaiseAction`, check every AX return code, verify with `NSWorkspace.frontmostApplication` after a short delay, and retry. (Tied to: cooperative activation docs [primary]; AX raise is best-effort [reports].)
7. **Pick the tap location deliberately.** Posting to `.cghidEventTap` is closest to real hardware but resets hid idle and HIDIdleTime, so the app's own jiggle would look like user activity. Either post to `.cgSessionEventTap` and read `hidSystemState` idle for real-user detection, or post to the HID tap and record your own post timestamps, treating the user as idle only when idle exceeds time since the last post plus slack. Test which tap Windows App actually forwards. (Tied to: local experiment [primary].)
8. **Jiggle on a 60 to 120 second cadence once local idle passes a threshold.** Teams goes Away at about 5 minutes, the RDS idle warning appears 2 minutes before disconnect, and the limit is whatever the admin set (the 10 to 15 minute figure seen in anecdotes is unsourced; default is unlimited [primary]). Stop immediately when real input resumes. (Tied to: Teams docs [primary]; RDS policy text [primary].)
9. **Restore state after each pulse.** Save and restore the frontmost app and cursor position; keep pulses short. The user is away, so focus stealing is acceptable but should be minimal. (Tied to: activation can bring forward unwanted windows [reports].)
10. **Hold a PreventUserIdleSystemSleep assertion while enabled; make display sleep prevention a toggle.** Mac sleep is a reported cause of drops independent of idle. Release on disable and quit; verify with `pmset -g assertions`. (Tied to: sleep-related drop reports [reports]; sjova/jiggle's assertions [primary].)
11. **Poll idle every 1 to 5 seconds instead of installing an event tap.** Avoids the Input Monitoring prompt and the tap-hang hazard. (Tied to: Apple forum hazard reports [reports].)
12. **Prefer `post(tap:)` over `postToPid`; test the latter only as an optional focus-free mode.** Evidence that postToPid delivers mouse events is weak. (Tied to: postToPid reports [reports].)
13. **Ship as a signed, non-sandboxed .app with LSUIElement, a fixed bundle id and a stable install path.** Request Accessibility with `AXIsProcessTrustedWithOptions` at launch, show a menu-bar warning when untrusted, and tell the user to relaunch after granting. Use a stable certificate so TCC grants survive rebuilds. (Tied to: sandbox and TCC identity reports [reports].)
14. **Use NSStatusItem plus NSMenu, and a library target plus thin executable in SwiftPM.** Disabled items for status lines, checkmarks for toggles, rebuild in `menuWillOpen`. Offer `SMAppService.mainApp` for launch at login and handle `.requiresApproval`. (Tied to: MenuBarExtra limits [reports]; local SwiftPM experiment [primary].)
15. **Include a diagnostic mode.** Let the user compare "jiggle in background" versus "focus and jiggle inside the window," and prompt them after N minutes to check the remote lock state and Teams status, so remote-lock problems can be separated from idle problems. (Tied to: nothing about forwarding is documented [primary by absence].)
16. **Document the limits and the policy caveat.** The app cannot beat a forced or manual lock with disconnect-on-lock, a gateway or VPN idle timeout that real input does not reset, Mac sleep or network and UDP drops. Treat Teams presence as a side benefit, not proof of delivery. The only policy discussion found treated idle bypass as a security concern, so say to use the app only where policy allows. (Tied to: session lock docs [primary]; AutoIt thread [reports].)

## Open questions / to verify empirically

1. Does Windows App 11.4.1 forward a synthetic `.mouseMoved` to the remote only while the session window is key, whenever the pointer is over it, or in the background? Test three cases: frontmost with pointer inside, frontmost with pointer outside, background with pointer inside.
2. Does a client-forwarded mouse-move reset the server idle timer the same as a click or key? Test with `query user` or a GetLastInputInfo-style counter inside the session.
3. Does a `.cgSessionEventTap` post reach Windows App's session view, or only a `.cghidEventTap` post?
4. Does `postToPid` deliver mouseMoved to Windows App without focus on macOS 27?
5. Which timer ends this user's session: RDS MaxIdleTime, an AVD or Windows 365 policy, Intune, remote screen lock with disconnect-on-lock, an RD Gateway CAP IdleTimeout, or a VPN or NAT device? Check `gpresult`, the registry, and TerminalServices-LocalSessionManager/Operational events (IDs 23, 24, 40, 4800 were cited by secondary sources and remain unverified; the MS troubleshoot page gives the dialog texts and registry values but no event IDs, so use the reason code in the event text rather than relying on specific IDs).
6. Does Teams on the remote PC measure idle from the Windows OS idle timer or from in-app activity, and does mouse-only motion reset it? Is a Teams mobile client signed in that could win the most-recently-active rule?
7. Do Windows App session windows expose stable `kAXTitleAttribute` values in the "<Name> Desktop" format for all connection types, including full-screen and Spaces cases?
8. Does a macOS 27 accessory app get its cooperative-activation request honored for another app? Compare `activate(from:options:)` with AX frontmost plus AXRaise.
9. Does macOS 27 require Input Monitoring or a separate Post Event grant for `CGEvent.post`, and does `CGEventSource` idle reading work with no permissions at all? Test with a fresh unsigned binary or after `tccutil reset`.
10. Are 1 to 2px moves enough to count as remote activity, or does the client only send moves that change the remote cursor position?
11. Does display sleep or Mac screen lock, as opposed to system sleep, break or starve a Windows App session?
12. Does `SMAppService.mainApp` register for an ad-hoc-signed app outside /Applications, and do Accessibility grants persist across ad-hoc rebuilds?
13. Does `.cgAnnotatedSessionEventTap` behave like `.cgSessionEventTap` for idle counters, and why did a privateState source posted to the HID tap reset CGEventSource idle but not HIDIdleTime?
14. Is there a hidden user-defaults key in com.microsoft.rdc.macos (like ClientSettings.EnableAvdUdpSideTransport) for keep-alive or idle behavior? Inspect `defaults read com.microsoft.rdc.macos` and the binary's strings.
15. Does the "Australia Desktop" connection go through RD Gateway or a VPN with its own idle limit, and is it a plain PC, AVD, Windows 365 or Dev Box connection?
16. Is Teams signed in on the Mac or a phone? Does remote Teams stay Available right up to the moment of each disconnect?
17. What exact dialog text and disconnect reason code accompany a drop (idle timeout code 3, lock, gateway, network)?
18. Is Windows App subject to App Nap while occluded, and does the Mac display sleep or lock while the user is away?
19. Does the Microsoft keep-alive policy (KeepAliveEnable/KeepAliveInterval) or a client keep-alive setting apply to this connection?
